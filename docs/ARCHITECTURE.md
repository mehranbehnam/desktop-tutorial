# معماری لیلیکا

## چرا کلاینت مستقیم، نه سرور واسط

سه راه برای ساختن پیام‌رسان روی تلگرام هست:

| روش | نتیجه |
| --- | --- |
| Bot API | فقط رباتی؛ به گفتگوهای شخصی کاربر دسترسی ندارد. برای پیام‌رسان بی‌فایده است. |
| سرور واسط MTProto | باید نشست همهٔ کاربران را نگه داری؛ یعنی مسئولیت امنیتی سنگین و یک نقطهٔ شکست. |
| **کلاینت مستقیم** | مرورگر خودش با دیتاسنتر تلگرام حرف می‌زند. کلید و نشست از دستگاه بیرون نمی‌رود. |

لیلیکا گزینهٔ سوم است. خروجی پروژه فقط فایل استاتیک است و هیچ سروری پیام‌ها را
نمی‌بیند.

```
┌────────────────────── مرورگر کاربر ──────────────────────┐
│                                                          │
│   components/  ──uses──►  store/  ──calls──►  lib/telegram│
│   (React, RTL)            (zustand)           (GramJS)    │
│                                                    │      │
└────────────────────────────────────────────────────┼──────┘
                                                     │ MTProto over WSS
                                                     ▼
                                          دیتاسنترهای تلگرام
```

## لایه‌ها

### `src/lib/telegram/` — تنها جایی که GramJS دیده می‌شود

هیچ کامپوننتی `Api.*` را مستقیم صدا نمی‌زند. هر چیزی که از این پوشه بیرون
می‌آید یک شیء سادهٔ قابل‌سریال‌سازی است با شناسهٔ **رشته‌ای** (GramJS `BigInt`
می‌دهد که نه در state ری‌اکت خوب می‌نشیند نه در JSON).

| فایل | مسئولیت |
| --- | --- |
| `client.ts` | ساخت/نابودی کلاینت، ذخیرهٔ نشست، مهلت اتصال |
| `auth.ts` | ورود، SRP دومرحله‌ای، ثبت‌نام، ترجمهٔ خطاهای RPC به فارسی |
| `dialogs.ts` | فهرست گفتگو، جستجو، سنجاق/بی‌صدا، علامت خوانده‌شدن |
| `messages.ts` | تاریخچه، ارسال متن و فایل، ویرایش، حذف، بازفرست، تایپینگ |
| `media.ts` | دانلود و کش عکس/فایل به‌صورت blob URL |
| `updates.ts` | ترجمهٔ آپدیت‌های زندهٔ MTProto به کال‌بک‌های تایپ‌دار |
| `utils.ts` | تبدیل موجودیت‌ها، thumbnail مات، entityهای متن |
| `types.ts` | مدل‌های نمایشی (`Peer`، `Message`، `Dialog`، …) |

### `src/store/` — وضعیت

سه استور zustand:

- **`authStore`** — ماشین حالت ورود. `stage` تنها منبع حقیقت برای این است که
  کدام صفحه رندر شود.
- **`chatStore`** — فهرست گفتگو + گفتگوی باز. پیام‌ها در یک نقشهٔ per-peer
  نگه‌داری می‌شوند و همیشه از قدیم به جدید مرتب‌اند.
- **`uiStore`** — پوستهٔ ظاهری و ترجیحاتی که با `localStorage` ماندگار می‌شوند.

### `src/components/` — رابط کاربری

هیچ کامپوننتی I/O مستقیم ندارد؛ همه از استورها می‌خوانند.

## تصمیم‌های قابل‌توجه

### مهلت اتصال

`client.connect()` در GramJS **حتی وقتی همهٔ تلاش‌های وب‌سوکت شکست بخورند هم
resolve می‌شود**. اگر فقط به آن تکیه کنی، رابط کاربری تا ابد روی «در حال
اتصال…» می‌ماند. بنابراین `createClient` بعد از connect وضعیت واقعی سوکت
(`client.connected`) را هم بررسی می‌کند و `isUserAuthorized()` هم داخل یک
مهلت زمانی اجرا می‌شود.

خطای شبکه هرگز به معنی «از حساب خارج شده‌ای» گرفته نمی‌شود: در آن حالت
`stage` روی `offline` می‌رود و نشست ذخیره‌شده دست‌نخورده می‌ماند.

### پیام خوش‌بینانه (optimistic)

پیام ارسالی بلافاصله با شناسهٔ منفی محلی در لیست می‌نشیند (آیکون ساعت)، و
وقتی سرور جواب داد با پیام واقعی جایگزین می‌شود. اگر ارسال شکست بخورد،
حباب با علامت خطا می‌ماند و متن از بین نمی‌رود.

### لنگر اسکرول

`MessageList` قبل از رندری که تاریخچهٔ قدیمی‌تر را به ابتدای لیست اضافه
می‌کند، `scrollHeight` و `scrollTop` را نگه می‌دارد و بعد اختلاف را برمی‌گرداند.
بدون این کار، هر بار بارگذاری صفحهٔ قبلی، جای خواندن کاربر می‌پرد.

### پیش‌نمایش مات

تلگرام همراه هر رسانه یک JPEG کوچک بدون هدر می‌فرستد. `strippedThumbToDataUrl`
هدر و فوتر استاندارد JPEG را به آن می‌چسباند تا مرورگر بتواند رمزگشایی کند —
همان کاری که کلاینت‌های رسمی می‌کنند. نتیجه: قبل از دانلود فایل اصلی، تصویر
مات دیده می‌شود.

### دانلود درخواستی

عکس و استیکر خودکار دانلود می‌شوند (همان چیزی که کاربر برایش اسکرول می‌کند)؛
ویدیو، صوت و فایل منتظر کلیک می‌مانند تا باز کردن یک کانال پرترافیک چند مگابایت
مصرف نکند. هر blob URL کش می‌شود و در `releaseAll` آزاد می‌شود.

### polyfill مرورگر

GramJS کتابخانه‌ای Node-first است و به `Buffer`، `process` و چند shim دیگر
نیاز دارد. `vite-plugin-node-polyfills` آن‌ها را فراهم می‌کند؛ بدون آن باندل
در زمان اجرا می‌شکند.

## چیزهایی که عمداً پیاده نشده

اینها با همین معماری قابل اضافه شدن‌اند:

- تماس صوتی و تصویری (نیاز به لایهٔ WebRTC تلگرام)
- ری‌اکشن، نظرسنجی تعاملی، تاپیک‌های فروم
- استیکر متحرک `.tgs` (نیاز به رندر Lottie)
- اعلان مرورگر و Service Worker برای حالت آفلاین
- رمزگذاری چت مخفی (MTProto secret chats)
